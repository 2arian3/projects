OptiServe / 01 Overview & problem

Serverless took away the servers. It didn’t take away the tuning.

Business problem
  • Lambda exposes exactly one performance knob — memory size — which proportionally allocates vCPU.
  • You pay for memory × time. More memory costs more per second, but the job also finishes faster. So the cost curve is U-shaped — there is a real sweet spot, and it’s different for every function.
  • ML workloads add a second knob: which model variant to serve. That moves latency, cost and output quality at once.
Why static config fails
  • The best setting depends on the data, not the code. A batch of 12-page records and a batch of 400-page records want different memory — from the same function.
  • Best parts don’t make a best whole. Tuning each function on its own doesn’t give you the best pipeline. An extra MB is worth more on the slowest path than off it.
  • Retries break your intuition. A step that loops back runs about 1.43× per request. “Tune the slowest function” is wrong when a fast one runs three times.
The engineering challenge
  • The space is combinatorial: 40,960 configurations for three functions. A ten-stage pipeline with four variants each is ~1017.
  • Every measurement costs real money and real wall-clock — you cannot brute-force in production.
  • Measurements are noisy: cold starts, busy servers, run-to-run variation. The optimizer has to cope with unreliable readings.
The business case, in one table — the App3 benchmark
DimensionRangeSpread
End-to-end latency2,955 – 81,280 ms27.5×

f1 → resnet → yolo, with a 0.3 back-edge and a 0.2 self-loop. A 27× latency and 8.5× cost spread across identical functional behaviour is the entire business case — and nobody tunes 40,960 configurations by hand.

Why this is an EvenUp problem

This is the same choice you make in a document pipeline: use the cheap model by default, and only call the expensive one when the cheap one isn’t sure — while staying inside limits on turnaround time, cost per case, and accuracy.

Different dial. Same problem.

OptiServe — 1 / 6
The U-shaped cost curve is the thing most people get wrong — say it explicitly: more memory can be CHEAPER, because duration falls faster than the per-ms price rises. Constraint interaction is the fourth point if they push: "under 5s p95" AND "under $X per thousand docs" AND "at least 0.9 accuracy" is not three independent problems.
OptiServe / 02 My role & ownership

What I built, and what was already there

I worked on this alone. The honest split: the search strategies come from published research. The engineering around them is mine.

Components I own end to end
  • The AWS wrapper. I tightened it until every AWS call in the project was 9 operations across 4 services, all in one folder. Nothing outside optiserve/aws/ talks to AWS at all.
  • Always put things back. Before changing anything, I save the function’s original settings. They get restored no matter how the run ends — success, crash, Ctrl-C, or being killed.
  • Runs you can resume. Progress is saved under a fingerprint of the run’s settings. Change a setting and you get a fresh run, instead of quietly mixing results that don’t belong together.
  • Acquisition-function vectorization. Rewrote update_knowledge from a Python loop to a NumPy kernel: 0.71 s → 0.0005 s, bit-identical output.
  • A cache. Keyed on the exact numbers, never rounded ones. Plus a second cache for the 54 % of the work that only depends on the pipeline’s shape.
  • Tests and CI. Took the AWS folder from 0 % to 76–100 % test coverage. The integration tests run twice, against two different fake-AWS setups.
  • Compat-flag discipline. Two optimizer bugs I could not simply fix became named flags with a baseline on both sides.
Judgement & communication
  • One noise-reduction trick makes results look cleaner but shifts the average by +1.3 %. I labelled it a METHODOLOGY WARNING in the code instead of hiding it.
  • Every result records which settings produced it, so numbers from different versions stay comparable.
Not mine — say this before they ask
  • The three search strategies come from published research, not from me. One mode reproduces the paper exactly, bugs included. What’s mine is the corrected version, the harness that measures how good the search actually is, and the switches that keep both honest.
  • The AWS wrapper classes already existed. I reviewed, hardened and tested them — which is how I found one method that nothing in the project ever called.
  • SciPy, networkx and moto do the numerical, graph and mocking work.

OptiServe / 04 Execution & data flow

One workflow, from live Lambda measurements to a chosen configuration

  1. 1
    Capture before mutating 900 s read timeout · adaptive retries, max_attempts=10
    ConfigManager.managed() issues GetFunctionConfiguration before any mutation, storing memory, timeout and MODEL_NAME for the finally.
  2. 2
    Resume or seed run_id = function__model__sha256(params)[:12]
    Sampler.exploration_init() checks the CheckpointStore for a matching parameter fingerprint; a hit restores samples and the pruned memory space.
  3. 3
    Apply and verify a memory default space: 2,881 memory steps
    UpdateFunctionConfiguration, block on the function_updated waiter, then verify memory and MODEL_NAME actually settled — a waiter returning is not convergence.
  4. 4
    Measure the configuration extra samples while CV > 5 %, up to 8
    Explorer fires one throwaway invocation to force a cold start, then fans out N concurrent invokes through a ThreadPoolExecutor.
  5. 5
    Parse and type failures markers first, numeric check as second signal
    Extracts Billed Duration from both the text REPORT line and the JSON platform.report, raising typed FunctionTimeout / NotEnoughMemory.
  6. 6
    Fit, then pick the next memory σ = 200 MB · converges in ~5–20 configurations
    Objective adds a Gaussian bump, ParamFunction refits rt(m)=a₀+a₁e^(−m/a₂) warm-started, then argmin(cost × knowledge) over the live space.
  7. ↓ the seam — below this line there is no AWS, no randomness, no I/O
  8. 7
    Cross the seam App3: 3 nodes · 1/4/4 variants · 16/16/10 steps
    add_ml_function evaluates every variant’s curve at every grid point into perf_profile[variant][memory].
  9. 8
    Model the application SFN overhead 18.81 ms/state, 1 ms/edge
    Copies the graph, de-loops with update_ne (self-loops → ne/(1−p)), reduces to a simple DAG, then evaluates latency and cost. Memoization is opt-in.
  10. 9
    Optimize, then score against truth greedy result vs. brute-forced ground truth
    Four corner configurations give the feasible envelope; greedy PRCP returns an OptimizationResult, which the evaluation harness scores against the brute-forced CSV.
The steps are the architecture. Steps 1–6 change a real AWS account, cost money, and give slightly different numbers each time. Steps 7–9 touch nothing, cost nothing, and give identical results every time. Anything I could make repeatable, I moved past step 7 — which is why the tests and the published numbers can be reproduced.
OptiServe — 4 / 6
Step 3 is the one to linger on — "a waiter returning is not the same as convergence" is a real distributed-systems lesson and it came from a real bug. Step 1's eager capture plus the finally is the answer to "what happens if it crashes mid-sweep": the customer's function is restored exactly as found, including removing MODEL_NAME if it wasn't there.

OptiServe / 06 Trade-offs & learnings

What I chose, what it cost me, and what broke

How to search
Greedy critical-path (PRCP)overexhaustive / ILP / Bayesian

Checking everything means 1017 options on a ten-step pipeline. The greedy approach is also easy to explain: you can point at which step got the next MB, and why.

Cost: no optimality guarantee. Paid for by brute-forcing ground truth and publishing the gap, tail included.

Where to split the system
One bridge methodovera live-AWS optimizer

Keeping everything unpredictable on one side of that method makes the other side give identical results every run, and free to test.

Cost: the discrete memory grid loses resolution the continuous curve had.

Fixing bugs vs. keeping results comparable
Named compat flagsoverjust fixing it

I found two bugs I couldn’t just fix. Fixing them changed numbers that my tests had locked in. So each one became a named on/off switch, with saved results for both settings. A test checks the two results really are different, so a switch can never quietly stop doing anything.

Cost: two code paths forever; two flags are still declared but ungated.

The thing I most want to remember

A cache that returns an almost right number is worse than no cache at all.

So the cache key uses the exact numbers, never rounded ones. If someone is going to publish your output, a tiny difference that only shows up when caching is on is a bug you will never track down.

Edge cases handled
  • Settings that can’t work. If a run hits out-of-memory or a timeout, that memory size becomes the new minimum. It never tries that range again.
  • Cold starts skewing results. One throwaway call per setting absorbs the cold start, so the measurements that count are all warm and comparable.
  • Loops and retries. Worked out with a formula for how many times each step runs on average, instead of simulating them.
  • AWS saying “done” isn’t done. After AWS reports the update finished, I read the settings back and check they actually changed.
Failure modes mitigated
  • A crash leaving someone’s function modified. Settings are saved up front and restored on every exit path, including being killed.
  • Getting rate-limited by AWS. The client slows itself down before AWS has to say no.
  • Quietly mixing results from different settings. The saved-progress key includes the settings, so changing one starts a new run.
  • Logging breaking the thing it’s logging. If writing an event fails, the run carries on regardless.
OptiServe — 6 / 6
The compat-flag story is the strongest single anecdote in this project — it shows you understand that in a system producing published numbers, "correct" and "comparable" are different requirements and you may have to serve both. Be ready for "why not just version the output?" — answer: because the golden battery is what proves the flag still does something, and a version number doesn't assert that.

Guardian / 01 Overview & problem

Move a 30-billion-parameter model onto one desktop machine, without rewriting the app

Business problem
  • Guardian handles medical emergencies at home. Sending an elderly person’s health data and speech to someone else’s API is a privacy risk.
  • Paying per word means an app that’s always listening has no cost ceiling.
  • A demo that dies when the venue WiFi dies is not a demo.
User impact
  • Everything runs on the machine. Nothing the user says leaves the room.
  • Shrinking the model to ~16 GB left enough room to run a second model alongside it.
  • Reachable over a private network, so the demo worked from anywhere — not just the venue’s wifi.
The engineering challenge
  • The app was written for one cloud API’s behaviour. Local models differ in how they split text, call tools, and think out loud.
  • The machine has one GPU and shared memory. There’s no fast dedicated video memory and no second GPU to fall back on.
  • I had to be able to swap the serving engine without touching app code, or I’d never have had time to compare three of them in a weekend.
The hardware correction I lead with, before anyone can catch it
  • A DGX Spark is one GPU and a 20-core ARM CPU on a single chip package. The link between them is NVLink-C2C — not NVSwitch, and not a multi-GPU setup.
  • So there was no tensor parallelism. You can’t split a model across GPUs when you only have one.
  • ~128 GB of memory shared by the CPU and GPU (121 GiB usable). There’s no separate video memory — nvidia-smi shows none, you check it with free -h.
  • The real constraint isn’t how the chips are wired together. It’s that this memory runs at ~273 GB/s, where a datacentre GPU gets several TB/s.
Why this is an EvenUp problem

A document platform needs the same gap between its extraction pipeline and whichever model it happens to use this quarter.

The pipeline shouldn’t know or care whether it’s talking to a hosted model or your own. Switching should be a config change, not a migration.

Guardian — 1 / 6
Say the hardware correction unprompted and early. Anyone who has touched a Spark knows it's a single-GPU desktop box; claiming NVSwitch or multi-GPU TP is the fastest way to lose the room. The honest story is better anyway — bandwidth-bound decode on LPDDR5X is a more sophisticated observation than "I used tensor parallelism". Keep TP/PP/NVSwitch in your pocket for the forward-looking question about scaling to an H200 node.
Guardian / 02 My role & ownership

I owned the model layer. The rest of the app was the team’s.

Three things, in the order I built them
1 The abstraction boundary
  • Every agent talks to one interface, using our own plain data types — Message, ToolSpec, ToolCall, LLMResponse.
  • The rule is written in the file itself: a vendor’s own objects must never leave the adapter.
  • Exactly one file imports a vendor library. That’s what made comparing three engines possible in a weekend.
2 The engine bake-off
  • Tested Ollama, vLLM and TensorRT-LLM with real conversations from the app, not made-up prompts. The app calls tools, so the benchmark had to as well.
  • Landed on TRT-LLM + a published NVFP4 checkpoint of Nemotron Nano 30B-A3B.
3 Production deployment
  • Ran TensorRT-LLM in a container behind an OpenAI-shaped endpoint, with the app and UI next to it.
  • Tuned the model’s memory reservation to 88 % of what was free in the shared 121 GiB pool.

The bug I’d talk about longest

The model’s “thinking” mode quietly broke the router. I gave it 24 words to pick an agent; it spent all 24 thinking, returned nothing, and every message fell through to the default agent. No error, anywhere.

The fix needed two layers, because the documented setting didn’t work on this backend: turn thinking off in the config and put /no_think at the start of the prompt.

Not mine

  • I used NVIDIA’s published 4-bit model. I didn’t shrink it myself.
  • I never benchmarked SGLang. I wanted to, and I ran out of weekend.
  • The voice feature exists in the code but wasn’t part of what I deployed or measured.

Guardian / 04 Execution & data flow

One utterance: “I feel a little dizzy. What should I do?”

  1. 1
    Ingress over Tailscale host port 8080
    Dashboard, Flutter app or watch POSTs {text, patient_id} to the FastAPI turn endpoint. CORS admits Tailscale, LAN and localhost origins.
  2. 2
    Turn setup and thread hop
    take_turn publishes a TranscriptEvent first, so the Live page resets before any step streams; the synchronous graph is dispatched via asyncio.to_thread with a thread-safe emit.
  3. 3
    Route — stage 1 zero model tokens
    Keyword scan over a tuple of emergency phrases. A match reaches the Safety agent directly. “Dizzy” is not in it, so we fall through.
  4. 4
    Route — stage 2 request #1 · max_tokens 24 · temperature 0.0
    Model classification call. For non-OpenAI providers the adapter sets enable_thinking=false and prepends /no_think — without both, every turn silently degrades.
  5. 5
    Agent prefill request #2
    LangGraph’s conditional edge selects the health node, which assembles [system + patient context, *history, user] and advertises its bound tool subset as JSON-Schema ToolSpecs.
  6. 6
    Wire encode, then the engine KV pool preallocated at 88 % of free memory
    Neutral DTOs → OpenAI wire format; POST crosses bridge → host. Prefill is compute-bound into paged KV blocks; decode is memory-bandwidth-bound, streaming ~1.5 GB of NVFP4 expert weights per step.
  7. 7
    Parse and normalize one bad tool call degrades; the turn survives
    nano-v3 strips the thinking block, qwen3_coder lifts native tool syntax into OpenAI-shaped tool_calls. Malformed JSON is stashed as {"_raw": ...} rather than raised.
  8. 8
    Tool execution and loop capped at MAX_TOOL_ROUNDS = 4
    registry.execute() runs each function, emit("tool_invocation") fires per tool so the dashboard lights up live, results append as role="tool", then back to step 5 with a longer prompt.
  9. 9
    Egress 2–5 sequential inference requests per user turn
    Returns {route, reply, tool_calls}; an AgentReplyEvent streams to SSE subscribers.
The ratio to internalize: one user-visible turn is 2–5 sequential inference requests, each with a longer prompt than the last. That is the answer to “why isn’t turn latency just request latency?” — and it is why the keyword fast-path in step 3 is worth having at all.

Guardian / 06 Trade-offs & learnings

What I chose, what it cost me, and what broke

Model precision
NVFP4overFP8 / INT4 AWQ

It reads half as much memory as FP8 per word (4× less than full precision). And on this GPU the maths itself runs at 4-bit. Other 4-bit methods only shrink storage — they unpack back to 16-bit before multiplying, so you save memory but not compute.

Cost: some accuracy loss I couldn’t put a number on, because I had no quality benchmark. FP8 was my fallback.

Serving engine
TensorRT-LLMoverOllama / vLLM

It had native 4-bit support for this GPU and handled several requests at once. Ollama was the easy baseline that proved the swap worked at all; vLLM was the sensible middle option.

Cost: a 10-minute startup, a pre-release build, and a backend that ignored a documented setting.

Container networking
Host for the engine, bridge for the appoveruniform bridge

The engine skips a network translation step on every request. The app stays isolated and reaches back across. Two different setups on purpose, not by accident.

Cost: a port clash to sort out, and two networking styles to keep straight in one file.

The thing I most want to remember

Matching an API’s shape isn’t the same as matching how it behaves.

The format was identical and every response came back as a valid HTTP 200. It still broke, because the model spent its whole budget thinking and returned nothing. No type check would have caught that.

Edge cases handled
  • Broken JSON from a shrunk model. Saved as raw text instead of throwing an error, so one bad tool call doesn’t kill the whole reply.
  • Runaway tool loops. Hard cap at MAX_TOOL_ROUNDS = 4.
  • One patient’s data leaking into another’s. Switching patients reloads their profile and clears the conversation history.
  • The API address is fixed at build time. Private-network IP first, local-wifi IP as backup — the browser runs on a different device than the server.
Failure modes mitigated
  • The router silently falling back to a default whenever the model started thinking — fixed in two places, because the documented setting didn’t work.
  • Timeouts set for a cloud model. Raised from 60 s to 120 s for the slower local one. That’s a config value, not something I measured.
  • Re-downloading 16 GB with hours left on the clock. The model cache lives outside the container, so rebuilding never re-downloads it.
  • Two models fighting over the same memory. Capped up front at 88 %, rather than finding the limit by crashing.

BakeryPilot / 01 Overview & problem

How do you let an AI touch real business data without letting it break anything?

Business problem
  • To answer “can we make 5,000 croissants in Toronto?”, a bakery manager has to check stock, recipes and schedules by hand across separate systems.
  • The answer usually means doing something — move butter from the other plant. That needs approval, a name attached, and a record.
  • An agent that can only answer is a toy. An agent that acts on its own is a liability.
User impact
  • Plain-English questions run against real stock, recipes and facilities — not fake data.
  • Every change shows up as a card someone has to approve, so a person stays accountable.
  • Status updates stream as it works (“checking stock levels”), so you see what it’s doing instead of a spinner.
The engineering challenge
  • The rules have to hold no matter who is writing — the agent, a seed script, the admin API, or a person with a database console.
  • Long-lived streaming responses through a proxy whose default settings break them.
  • Deploying to one live server, where a failed database migration means lost data, not a quick undo.
Three corrections I make before anyone asks
  • It isn’t GCP. It’s one Ubuntu server on OpenStack, deployed by a runner installed on that same server. The skills carry over exactly — but I say OpenStack, because that’s what it is.
  • No search-by-meaning shipped. The database extension is installed, but there are no embeddings and no similarity queries. I designed the schema for it, then cut the feature at about 36 hours to protect what already worked.
  • No HTTPS. It’s plain HTTP on port 80. I wrote up three ways to add TLS instead, which I’d rather be able to explain than have copy-pasted one command.
Why this is an EvenUp problem

“Never let an AI write client-facing data without review” is the rule in legal tech.

Here the structure enforces it: the agent has no way to write to real tables at all. The worst it can do is leave an unapproved card sitting there.

BakeryPilot / 02 My role & ownership

The database, the proxy, and the deployment pipeline

Components I own end to end
  • The database schema and its safety net. 34 tables, 47 foreign keys, 35 check rules, and 5 tables you cannot edit or delete from. Corrections are new rows that cancel out the old ones. The database refuses the edit outright.
  • The human approval gate. Six kinds of card, each pending until someone accepts or rejects it. Deciding twice is rejected. On approval, the card, the data change and the audit trail all land in one transaction.
  • The Nginx proxy. Tuned for long-lived streams: buffering off, caching off, a one-hour read timeout, and reused connections to the backend.
  • The deploy pipeline. The runner lives on the server, so there are no deployment secrets anywhere — no SSH key, no service-account file, nothing stored in GitHub. Deploys are queued so two can never overlap.
  • Migration safety. A database backup before every schema change, keeping the last 30. Migrations stop on the first error. The proxy config is validated before it’s reloaded.
  • A three-level prompt store. A short-lived cache first, then MongoDB with a 2-second timeout, then prompt files shipped with the app. If Mongo goes down it stops trying and uses the files.
Judgement & communication
  • Made the call to cut a feature. At about 36 hours I dropped search-by-meaning to protect the parts that worked, and kept the schema design that would make it easy to add later.
  • Sorted every dependency by one question: if it goes down, do we give wrong answers, or just fewer features? Only the second kind got a fallback.
Not mine
  • The web frontend and the product design were my teammates’ work.
  • The eight specialist agents and their prompts were a shared effort. I built the tool layer they call through.
  • LangGraph, SQLAlchemy, Alembic and Nginx do the heavy lifting for orchestration, database access, migrations and proxying.

BakeryPilot / 06 Trade-offs & learnings

What I chose, what it cost me, and what broke

How to run the agent
In-process library importovera separate agent service

It removed a network hop, a health check and a restart loop, and cost nothing — because the agent never needed to scale separately.

Cost: the backend image has to be built from the repo root, because it depends on the agent folder next door.

Search feature
Descope semantic retrievalovera half-built RAG layer

I put the vector store inside Postgres so embeddings and rows would save together in one transaction — consistency for free. Then I cut the feature at ~36 hours to protect what already worked.

Cost: an empty feature sitting there. I say “designed, not shipped” every time it comes up.

Should deploys wait for tests?
CD parallel to CIoverCD gated on CI

At a hackathon, a flaky test blocking a demo fix was the bigger risk. It was deliberate, and it’s written in the workflow file.

Cost: a red build deploys. Correct for a demo, wrong for production — and it’s the first thing I’d change.

The thing I most want to remember

The bug was never the streaming. It was a 60-second timeout hiding behind a buffering problem.

The chat looked frozen, then dumped everything at once. I called the app directly, bypassing the proxy, and the text arrived bit by bit. So the backend was fine and the proxy was the problem. Working out which layer was at fault was the real work. The one-line fix was the easy part.

Edge cases handled
  • Approving the same card twice. The second attempt is rejected, checked before anything runs.
  • Transfers that can’t be fully filled. The shortfall is written down, so the record shows what was missing instead of quietly claiming success.
  • The API address is baked in at build time. Changing the environment variable isn’t enough — the frontend has to be rebuilt.
  • MongoDB going down. Three levels of fallback, and once it fails the app stops retrying and uses the bundled files.
Weak spots I’d name before you found them
  • Deploys don’t wait for tests. They run side by side, so a failing build still ships.
  • There is downtime on deploy. The old container stops before the new one starts, so the site errors for that window.
  • No automatic rollback. There’s always a backup and a revert-and-push path — manual, but quick.
  • One server, one copy of every service. Nothing is redundant.
The fix I’d ship first: blue/green behind the Nginx I already built — flip the upstream block and nginx -s reload. An upstream swap, not a new architecture.

Synthesis / 01

Three projects, three habits worth keeping

1 Keep the model behind one door

In each project, the slow and unpredictable part sits behind one small interface.

  • OptiServe: all of AWS is 9 operations in one folder. Nothing outside it talks to AWS.
  • Guardian: exactly one file imports a vendor library, so moving from cloud to local was a config edit.
  • BakeryPilot: the agent is just another API client. No direct database access, no special privileges.
Why it pays off: 137 of OptiServe’s 155 tests run with no internet. Easy testing is the reward, not the reason.
2 Measure first, then optimize

Every performance claim in this deck comes from a command you could re-run yourself.

  • OptiServe checks every option the slow way, so the 96–99 % figure is measured, not claimed.
  • The 2.99× speed-up came after profiling showed one function was 77 % of the runtime.
  • Where I never measured something — Guardian’s speed — this deck says so instead of making a number up.
Why it pays off: a number that falls apart under one follow-up question costs more than it was ever worth.
3 Make the answer checkable

In all three, the output outlives the run that produced it. Someone will ask about it later.

  • OptiServe caches on exact numbers, never rounded ones. An almost-right cached answer is worse than no cache.
  • BakeryPilot blocks edits to history in the database itself, not in application code.
  • Forecasts record which model version made them, so v3’s answers stay reproducible after v4 ships.
Why it pays off: it’s what a legal document needs — who claimed what, from which page, using which model.

Synthesis / 02

Raw medical records → structured extractions

Assume a background job with hours to finish, messy scanned PDFs, and a human reviewing before delivery. Speed is not the hard part.

1 Name every file by its contents

Store each page under a hash of its own bytes. Duplicates disappear for free — the same record from three providers is stored once — and that hash plus the stage and model version becomes a natural key for “have we already done this?”

2 Make skipping work its own step

Plenty of “scanned” records already have real text in them. A cheap check that sends those straight past OCR is the highest-value box in the diagram. Then do the same thing one step later: use the small model by default, and only call the big one when confidence is low.

This is OptiServe’s idea, applied here

Pick a different model per step, trading speed against cost against accuracy — and spend your effort on the step that actually moves the total, not evenly across all of them.

Synthesis — 2 / 3
Spend the first sentences clarifying, not designing: interactive or background? one merged PDF or many files? human review before or after delivery? per-field or per-document accuracy bar? Then name the hard part out loud: (a) a 4,000-page case failing at page 3,700 must not restart; (b) every fact must be traceable to a source page or it is worthless in a legal document; (c) cost is dominated by which model runs on which page, not by infrastructure. Queue-between-every-stage gives backpressure free and isolates poison pills. Avoid Airflow — it is built for scheduled batch DAGs, not 100k concurrent per-entity workflows.
Synthesis / 03

The questions I’d expect you to ask

Four places this design has to hold up, and how I’d answer.

“How do you guarantee exactly-once?”

You don’t — and that’s the right answer. You can’t guarantee a message is delivered exactly once over a network. You can guarantee it has the same effect once: deliver at least once, and make each step safe to repeat. Every stage writes under the same key, so a repeat just overwrites with identical data.

The one place to be careful is the AI call itself. It’s expensive, so check whether you already have the answer before making it.
“One stage is 10× slower than the rest.”

Start by measuring, not guessing. Queue length and how old the oldest item is tell you exactly where the backlog sits. Then fix that one stage: more workers if it’s waiting on I/O, batching if the per-call overhead dominates, a cheaper model if it’s cost.

Don’t scale the whole pipeline evenly. That’s exactly the mistake OptiServe’s search exists to avoid.
“The LLM provider has an outage.”

Stop calling the broken provider, switch to a backup or a smaller local model, and record which model actually did the work, so your quality numbers don’t quietly mix two different models together.

If you have hours to finish, the queue absorbs a 20-minute outage completely. That’s the main reason to use queues here instead of direct calls.
“How do you control cost?”

Three levers, biggest first: (1) don’t do the work at all — skip duplicates and pages that already have text; (2) use the smallest model that works for each page; (3) cache on the content hash, because the same forms show up again and again across cases.

Then track cost per case next to quality, with the model version attached — so an accuracy win that doubles your bill shows up on the same dashboard.
